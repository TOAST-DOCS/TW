# 인스턴스 간 내부 통신에 실패합니다

## 증상

같은 VPC 안에 있는 인스턴스끼리 통신이 되지 않습니다. SSH, ping 또는 애플리케이션 포트(예: TCP 9091)로 접속을 시도하면 아래 메시지와 같이 연결이 타임아웃되거나 거부됩니다.

{% tabs %}
{% tab title="telnet" %}
```
$ telnet {대상 인스턴스 IP} {포트}
Trying {대상 인스턴스 IP}...
telnet: Unable to connect to remote host: Connection timed out
```
{% endtab %}
{% tab title="SSH" %}
```
$ ssh user@{대상 인스턴스 IP}
ssh: connect to host {대상 인스턴스 IP} port 22: Connection timed out
```
{% endtab %}
{% tab title="ping" %}
```
$ ping {대상 인스턴스 IP}
PING {대상 인스턴스 IP} ({대상 인스턴스 IP}): 56 data bytes
Request timeout for icmp_seq 0
```
{% endtab %}
{% endtabs %}

같은 서브넷 안의 인스턴스끼리 안 되는 경우도 있고, 서로 다른 서브넷에 있는 인스턴스끼리 안 되는 경우도 있습니다. 다음과 같은 상황에서 발생할 수 있습니다.

- 보안 그룹 규칙을 변경한 직후
- 새 인스턴스를 생성한 직후
- 인스턴스를 중지했다가 다시 시작한 직후

## 빠른 확인

다음을 먼저 확인하세요. 많은 경우 여기서 원인을 찾을 수 있습니다.

1. 양쪽 인스턴스에 적용된 Security Groups 규칙을 확인합니다. **Network > Security Groups**에서 해당 보안 그룹을 선택하면 하단에 **보안 규칙** 탭이 나타납니다. 규칙 목록에서 **방향** 열이 "수신"인 규칙과 "송신"인 규칙을 모두 확인하고, 상대 인스턴스의 IP와 포트가 허용되어 있는지 확인합니다.
2. 인스턴스에 SSH로 접속할 수 있다면, OS 방화벽 상태를 확인합니다.
   - Linux: `sudo iptables -L -n` 또는 `sudo firewall-cmd --list-all`
   - Windows: `netsh advfirewall show allprofiles`

## 원인과 해결 방법

인스턴스 간 내부 통신이 안 되는 원인은 다양합니다. 아래 흐름도에서 원인을 좁힌 뒤, 해당하는 원인의 해결 방법을 적용하세요.

![인스턴스 간 내부 통신 실패 진단 흐름도](https://github.com/TOAST-DOCS/TW/blob/master/task-guide/ko/images/instance-internal-communication-failure-diagnosis-flow.svg)

### 원인 1: 보안 그룹 규칙 설정 오류

Security Groups는 인스턴스에 대한 네트워크 접근을 제어하는 가상 방화벽입니다. 명시적으로 허용한 규칙에 해당하는 트래픽만 통과시키므로, 규칙이 누락되거나 잘못 설정되면 통신이 차단됩니다.

Security Groups는 stateful 방화벽입니다. 수신 규칙으로 허용된 연결의 응답 트래픽은 송신 규칙이 없어도 자동으로 허용됩니다. 반대로, 송신 규칙으로 허용된 연결의 응답도 수신 규칙 없이 자동으로 들어옵니다. 따라서 확인해야 할 것은 **새 연결을 시작하는 방향**의 규칙입니다.

다음과 같은 설정 오류가 자주 발생합니다.

- **수신 규칙 누락**: 인스턴스 A에서 인스턴스 B의 TCP 9091로 접속하려면, 인스턴스 B의 보안 그룹에 방향 "수신", 프로토콜 TCP, 포트 9091을 허용하는 규칙이 있어야 합니다. stateful이므로 응답 트래픽(B→A)은 별도 규칙 없이 허용됩니다.
- **송신 규칙 누락**: 인스턴스에서 다른 인스턴스로 새 연결을 시작하는 경우, 연결을 시작하는 인스턴스의 보안 그룹에 방향 "송신" 규칙이 필요합니다. 기본 보안 그룹(default)은 송신을 모두 허용하지만, 커스텀 보안 그룹을 만들면서 송신 규칙을 추가하지 않으면 나가는 트래픽이 차단됩니다.
- **프로토콜 또는 포트 번호 불일치**: TCP 포트를 열었는데 UDP 트래픽을 보내거나, TCP 22번을 열었는데 TCP 9091번으로 접속을 시도하면 차단됩니다. ICMP(ping)는 TCP/UDP와 별개이므로 별도로 허용해야 합니다.
- **원격 IP 범위(CIDR) 오류**: 허용한 CIDR 범위가 상대 인스턴스의 IP를 포함하지 않는 경우입니다. 예를 들어 `10.0.0.10/32`만 허용했는데 `10.0.0.20`에서 접속하면 차단됩니다.

**해결 방법**

1. **Network > Security Groups**에서 양쪽 인스턴스에 적용된 보안 그룹을 각각 선택합니다. 인스턴스에 적용된 보안 그룹은 **Compute > Instance**에서 인스턴스를 선택한 뒤 **기본 정보** 탭의 **보안 그룹** 항목에서 확인할 수 있습니다.
2. 보안 그룹의 **보안 규칙** 탭에서 규칙 목록을 확인합니다. 접속을 받는 인스턴스의 보안 그룹에 방향 "수신", 상대 IP를 포함하는 원격 CIDR, 올바른 프로토콜과 포트 범위가 허용되어 있어야 합니다.
3. 보안 그룹을 여러 개 사용하고 있다면, 필요한 보안 그룹이 해당 인스턴스에 모두 적용되어 있는지 확인합니다.
4. ping 테스트가 필요하면 ICMP를 별도 규칙으로 허용합니다.

### 원인 2: 서브넷 간 라우팅 설정 오류

같은 VPC에 속한 서브넷이라도, 라우팅 경로가 올바르지 않으면 서브넷 간 트래픽이 전달되지 않습니다. 특히 방화벽 어플라이언스(UTM, VPN 등)를 각 서브넷의 게이트웨이로 사용하는 환경에서, 라우팅 테이블에 대상 서브넷으로의 경로가 누락되거나 게이트웨이 IP가 잘못 지정되면 패킷이 올바른 경로로 전달되지 않습니다.

Floating IP를 통한 외부 접근은 정상이고 사설 IP를 통한 내부 접근만 안 되는 경우, 라우팅 설정을 의심합니다.

> [!NOTE]
> 같은 서브넷 내 인스턴스끼리 통신이 안 되는 경우에는 라우팅이 원인일 가능성이 낮습니다. 같은 서브넷 내 트래픽은 라우팅 테이블을 거치지 않고 직접 전달됩니다. 이 경우 원인 1(보안 그룹) 또는 원인 3(OS 방화벽)을 먼저 확인하세요.

먼저 같은 서브넷 내 인스턴스끼리 통신이 되는지 확인합니다. 같은 서브넷은 되고 다른 서브넷만 안 되면 라우팅 문제로 좁혀집니다.

**해결 방법**

1. **Network > Routing**에서 해당 VPC의 라우팅 테이블을 선택한 뒤 **라우트** 탭을 확인합니다. 대상 서브넷의 CIDR로 향하는 경로가 존재하는지, 게이트웨이가 올바른지 확인합니다.
2. 방화벽 어플라이언스를 게이트웨이로 사용하고 있다면, 방화벽의 라우팅 규칙과 보안 정책에서 대상 서브넷 간 트래픽이 허용되어 있는지 확인합니다.

### 원인 3: OS 레벨 방화벽 차단

Security Groups와 별개로 인스턴스 OS 내부의 방화벽이 트래픽을 차단할 수 있습니다. Security Groups에서 허용했더라도 OS 방화벽에서 해당 포트를 차단하면 통신이 안 됩니다. Linux의 iptables/firewalld, Windows의 Windows Firewall이 해당합니다.

**해결 방법**

접속을 받는 인스턴스에서 OS 방화벽 상태를 먼저 확인합니다.

{% tabs %}
{% tab title="Linux" %}
1. 방화벽 규칙을 확인합니다.

   ```sh
   # iptables 기반
   sudo iptables -L -n

   # firewalld 기반
   sudo firewall-cmd --list-all

   # 특정 포트 차단 여부 확인
   sudo iptables -L -n | grep {포트}
   ```

2. 차단 규칙이 있다면 해당 포트를 허용합니다.

   ```sh
   # iptables에서 특정 IP의 특정 포트 허용
   sudo iptables -A INPUT -s {소스 IP} -p tcp --dport {포트} -j ACCEPT
   sudo iptables-save

   # firewalld에서 포트 허용
   sudo firewall-cmd --add-port={포트}/tcp --permanent
   sudo firewall-cmd --reload
   ```

3. SELinux가 활성화된 환경에서는 SELinux 정책이 네트워크 포트를 제한할 수 있습니다.

   ```sh
   # SELinux 상태 확인
   getenforce

   # Enforcing 상태라면 일시적으로 비활성화해 테스트
   sudo setenforce 0
   ```

    > [!NOTE]
    > `setenforce 0`은 재부팅 전까지만 유효합니다. SELinux가 원인으로 확인되면 해당 포트를 SELinux 정책에 영구 등록하는 것을 권장합니다.
{% endtab %}
{% tab title="Windows" %}
1. 방화벽 상태와 수신 규칙을 확인합니다.

   ```cmd
   netsh advfirewall show allprofiles
   netsh advfirewall firewall show rule name=all dir=in
   ```

2. 차단되어 있다면 해당 포트를 허용합니다.

   ```cmd
   netsh advfirewall firewall add rule name="Allow TCP {포트}" dir=in action=allow protocol=tcp localport={포트}
   ```
{% endtab %}
{% endtabs %}

### 원인 4: 인스턴스 네트워크 일시적 장애

보안 그룹, 라우팅, OS 방화벽이 모두 정상인데 특정 인스턴스에서만 통신이 안 되는 경우가 있습니다. 같은 서브넷에서 같은 보안 그룹을 적용한 다른 인스턴스는 정상인데 한 인스턴스만 안 되는 상황입니다. 이 경우 인스턴스가 위치한 하이퍼바이저 수준의 일시적 네트워크 이슈일 수 있습니다.

> [!WARNING]
> 인스턴스를 중지하면 실행 중인 프로세스가 중단됩니다. 운영 중인 서비스라면 영향 범위를 확인한 뒤 진행하세요.

**해결 방법**

1. 인스턴스 외부(네트워크/하이퍼바이저)에서 트래픽이 차단되고 있는지 먼저 확인합니다. 예를 들어 Linux 환경이라면 `tcpdump`를 이용해 패킷이 인스턴스에 도달하는지를 확인할 수 있습니다. 상대 인스턴스에서 접속을 시도하는 동안 아래 명령을 실행합니다.

   ```sh
   sudo tcpdump -i eth0 host {상대 인스턴스 IP} and port {포트}
   ```

    패킷이 보이지 않으면 인스턴스 외부에서 트래픽이 차단되고 있는 것입니다.

2. 인스턴스 **재부팅**이 아니라 **중지 후 시작**으로 조치합니다. 재부팅은 같은 하이퍼바이저에서 다시 시작하지만, 중지 후 시작하면 다른 하이퍼바이저에 배치될 수 있습니다.

   **Compute > Instance**에서 대상 인스턴스를 선택한 뒤 추가 메뉴에서 **인스턴스 중지**를 클릭하고, 중지가 완료되면 **인스턴스 시작**을 클릭합니다.

    > [!NOTE]
    > **인스턴스 종료**는 인스턴스를 삭제하는 동작이므로 주의하세요. 통신 문제 해결을 위해서는 **인스턴스 중지** 후 **인스턴스 시작**을 사용합니다.

3. 시작 후 통신이 정상으로 돌아왔는지 확인합니다. 중지 후 시작으로도 해결되지 않으면 문의하기로 진행합니다.

## 문의하기

위 방법으로 해결되지 않으면 [NHN Cloud 고객지원](https://www.nhncloud.com/kr/support/inquiry)에 문의하세요. 인스턴스 간 통신 문제 중 일부는 플랫폼 측 원인으로 발생하며, 이 경우 NHN Cloud의 확인·조치가 필요합니다. 문의 시 다음 정보를 함께 전달하면 빠른 진단에 도움이 됩니다.

- 통신이 안 되기 시작한 시각(KST 기준)
- 프로젝트 ID(**프로젝트 관리** 탭 > **프로젝트 기본 정보**에서 확인)
- 양쪽 인스턴스의 ID와 사설 IP
- 양쪽 인스턴스에 적용된 보안 그룹의 보안 규칙 목록(스크린샷 또는 **보안 규칙 목록 다운로드**)
- 접속을 시도한 프로토콜과 포트 번호
- OS 방화벽 상태(`sudo iptables -L -n` 또는 `sudo firewall-cmd --list-all` 출력)
- `tcpdump` 결과(패킷 도달 여부)
- 같은 서브넷의 다른 인스턴스에서는 통신이 되는지 여부
